# Подготовка основной задачи

Работай в выбранной роли. Сначала прочитай [правила источников](../../../standards/source-policy.md) и [качество требований](../../../standards/requirements-quality.md). При выборе профилей используй [формат профилей](../../../docs/profile-format.md); не загружай несвязанные навыки и проекты.

Изучи исходное описание, родителя, релевантные связанные требования и существующие подзадачи. Если что-то недоступно, обозначь ограничение. Для улучшения сохрани согласованные ID и смысл требований; кратко выдели существенные изменения описания.

Подготовь минимально достаточный текст:

- Цель и ожидаемый бизнес-результат, без придуманных метрик.
- User story, когда она поясняет пользователя и ценность.
- Сценарии/use cases и существенные исключения, когда одного требования недостаточно.
- Данные, если их состав, источник или правила меняют поведение.
- Функциональные требования со стабильными ID, проверяемые и соразмерные задаче.
- Границы изменения; открытые вопросы с влиянием и владельцем решения, если он известен.

Отдельные критерии приёмки добавляй только при дополнительной ценности для проверки. Не повторяй одни и те же условия в сценарии, требованиях и приёмке. Удали неиспользуемые разделы. [Шаблон](assets/task-template.md) — основа для результата, а не обязательный перечень заголовков.

Не придумывай отсутствующие бизнес-решения. В роли бизнес-аналитика не проектируй реализацию. В роли системного аналитика отделяй подтверждённое поведение и контракты от предложений; неизвестный API обозначай вопросом.

Верни описание, использованные источники/статусы и открытые вопросы. По умолчанию это черновик в ответе или указанном локальном файле. Если пользователь явно поручил обновить описание в трекере, проверь целевую задачу, её актуальную версию и согласованный объём, затем обнови без повторного разрешения. При конфликте версии сохрани новое чужое содержание и согласуй только возникшее расхождение; после неопределённого результата записи сначала перечитай задачу, не повторяй запись вслепую.
