# Результаты первого прогона

Дата: 2026-10-19. Версия: 0.1.0. Входы: [scenarios.md](scenarios.md).

Метод: авторский ручной прогон текущим агентом по написанным инструкциям, с фиксацией решений ниже. Это не независимая оценка другой моделью и не автоматический тест активации скиллов в клиенте. Внешний трекер не подключался, задачи не изменялись. «Пройден» означает соответствие указанным критериям на этих синтетических входах, а не гарантию будущего поведения модели.

## S1 — пройден

Получены [описание](../examples/task-description.md) и [декомпозиция](../examples/decomposition.md). В описании только цель, два проверяемых FR, границы и источник. User story, отдельные сценарии и приёмка не добавлены, так как не уточняют результат.

Результат декомпозиции — W1, development, create; FR-1 и FR-2 покрыты одной работой. Дизайн и аналитика не нужны по входу; проверка включена в W1, отдельного тестирования нет. Тип и ID не определены, внешних записей нет. Ограничение доступа не изменяется.

## S2 — пройден

Контекст: system-analyst, example-team/example-project, decompose-task, prepare. Источники `sla-brief-v1` и `sla-system-v1` согласованы только для S2; подзадач нет. Все четыре работы — предложения create, типы/ID трекера не определены.

| ID / категория / название | Цель и результат | Объём и границы | Требования | Зависимости и проверка |
| --- | --- | --- | --- | --- |
| A1 / analysis / Согласовать получение SLA | Контракт чтения для потребителя UI | Уточнить единицы времени, отсутствие значения и недоступность с владельцем сервиса; не назначать неизвестные поля API | SLA-1, SLA-2 | Нет предшественников; результат сверить и согласовать с функцией владельца сервиса SLA |
| D1 / design / Определить состояния индикатора SLA | Согласованное представление обычного и недоступного состояния | Макет/описание двух состояний; без изменения правил расчёта SLA | SLA-1, SLA-2 | Первичный дизайн параллелен A1; окончательное согласование после A1, проверка покрытия обеих ситуаций функцией дизайна |
| W1 / development / Реализовать индикатор SLA | UI отображает полученное значение или недоступность | Интеграция по результату A1 и отображение по D1; расчёт SLA не переносится в UI | SLA-1, SLA-2 | Заблокирована согласованными A1/D1; предварительный объём уточнить после них |
| T1 / testing / Проверить индикатор с сервисом SLA | Результат отдельной интеграционной проверки | Проверить доступный источник и недоступность; без полного регресса несвязанных функций | SLA-1, SLA-2 | После W1 и доступной согласованной тестовой среды; приложить факт отображения для обоих случаев |

Покрытие: SLA-1 → A1/D1/W1/T1, SLA-2 → A1/D1/W1/T1. Проверка SLA-1 — значение, соответствующее согласованному контракту; SLA-2 — состояние недоступности без ложного актуального значения. Порядок A1 → окончательный D1 → W1 → T1, первичный D1 может идти параллельно A1; цикла нет. Разработка ещё не готова. Endpoint, поля, таймауты и точные единицы не выдуманы.

## S3 — пройден

Контекст: system-analyst, example-team/example-project, decompose-task, prepare. Использованы согласованные FR-1/FR-2 и предоставленный актуальный текст DEMO-11.

Предложение `update DEMO-11`, development: название «Добавить выбор статуса и сброс»; цель — полный результат фильтрации. Сохранить реализацию и проверку FR-1, дополнить объём сбросом по FR-2 и проверкой возврата всех доступных записей. Новых задач не предложено. Вне объёма — изменение доступа и сохранение фильтра; зависимостей по входу нет. Тип/ID неизвестны. Покрытие FR-1 → существующая часть DEMO-11; FR-2 → предлагаемое дополнение DEMO-11. Изменений в трекере нет.

## S4 — пройден

В отчёте есть место, проблема, основание, влияние, исправление и блокирующий признак. Рекомендовано дополнить W1, а не создавать искусственную новую подзадачу. DOR-4 не выполнен; сведения о среде отдельно отмечены как «нет данных». Источники не изменены.

## S5 — пройден

Контекст: business-analyst, example-team/example-project, describe-task, черновик. Прочитаны export-approved-v1/EXP-1 (approved), export-draft-v2/EXP-1 (draft) и похожая задача (example).

Полученное описание: цель — ограничить объём выгрузки согласованным правилом; подтверждённое текущее EXP-1 — не более 100 записей по approved-v1. В отдельном конфликте указано, что draft-v2 предлагает 500, отмена v1 не подтверждена. Значение 1000 из примера не перенесено. Вопрос функции владельца продукта: «Заменяет ли v2 согласованный лимит 100 и для какой области выгрузки?» Влияние — границы реализации и проверка максимума. До ответа изменение лимита на 500 не готово к передаче в разработку. Новая реализация выгрузки и API не спроектированы.

DoD сформирован из DOD-1…DOD-4 и TEAM-DOD-1: реализация и применимое ревью; результаты интеграционной проверки/решения по дефектам; актуализация затронутого контракта и описания состояний; передача результата с источниками и ограничениями. Ожидаемые подтверждения — ссылки на реализацию/ревью, отчёт проверки, актуальные документы и передачу. Функциональные SLA-1/2 не переписаны в DoD. По входу реализация, проверки и передача не выполнялись; готовность к завершению не подтверждена.

## S7 — пройден

Контекст: system-analyst, example-team/example-project, decompose-task prepare и review-task. Источники: подтверждённое наблюдение filter-observation-v1 и согласованное FR-2; полного воспроизведения нет.

Получен черновик B1, create, subbug, «После сброса фильтра остаётся пустой список». Цель — устранить подтверждённое расхождение с FR-2. Факт: пустой список при наличии доступной заявки; ожидание: все доступные заявки после сброса. Объём — диагностика и устранение именно этого расхождения, без изменения правил доступа. Тип/ID неизвестны. Проверка после уточнения воспроизведения — повторить исходный случай и подтвердить FR-2.

Среда, версия, предусловия, точные шаги, данные и частота записаны как неизвестные; реконструированные шаги за факт не выданы. Блокер начала исправления — воспроизводимый случай или достаточное диагностическое доказательство. Черновик не готов к исправлению.

Ревью B-R1, **недостаток информации**. Место: B1, раздел «Воспроизведение». Проблема: по входу невозможно повторить наблюдение. Основание: в filter-observation-v1 нет среды, версии и шагов; влияние — невозможно надёжно локализовать и проверить устранение. Исправление: запросить эти сведения у автора наблюдения, владельца по имени не придумывать. Блокирует: да, начало исправления по DOR-5; отдельно нужен владелец вопроса по TEAM-DOR-1. Это не рекомендация по стилю и не основание выдумать шаги.

## Структурные проверки и границы

Все четыре SKILL.md прошли `quick_validate.py` из установленного skill-creator. Для проверки использован уже установленный Python с PyYAML и режимом UTF-8; новые зависимости не устанавливались. В некоторых других локальных Python PyYAML отсутствует — это не требование для использования библиотеки.

Финальные запуски завершились с кодом 0:

| Проверка | Фактический результат |
| --- | --- |
| `checks/validate.py` | 35 непустых файлов, 4 скилла, 48 локальных ссылок, 0 ошибок |
| `checks/validate.py --yaml` | Те же проверки плюс 11 YAML-документов, включая frontmatter скиллов; 0 ошибок |
| `quick_validate.py` skill-creator | 4 из 4 скиллов валидны |
| Ручной прогон S1–S8 | 8 из 8 соответствуют критериям; решения приведены выше |

Первый структурный запуск обнаружил неверную глубину ссылок на общие стандарты в SKILL.md; ссылки исправлены и проверены повторно. Скрипт не выполняет поведенческие сценарии и не доказывает актуальность метаданных внешнего трекера.

Реальная запись, обработка сетевого таймаута и обнаружение навыков в новой сессии клиента здесь не испытывались. Для начала работы с реальным проектом нужны его источники и метаданные; для записи — отдельное явное поручение пользователя.
