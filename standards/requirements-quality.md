# Качество требований

- Цель объясняет ожидаемый бизнес-результат. Если метрика или целевое значение неизвестны, обозначь вопрос, а не выдумывай число.
- Требование описывает наблюдаемое поведение и существенные условия, без слов «удобно», «быстро», «корректно» без проверяемого смысла.
- Указывай исполнителя, триггер и результат там, где иначе возникает неоднозначность. Основной сценарий дополняй исключениями, которые меняют результат или границы.
- Бизнес-правила и ограничения должны иметь источник. Не смешивай факты, решения, предложения и вопросы.
- Стабильные ID требований полезны для покрытия. Для маленькой задачи достаточно одного `FR-1`; не перенумеровывай уже согласованные ID без необходимости.
- Данные описывай, если состав, источник, обязательность или доступ влияют на поведение. Не добавляй схему БД ради шаблона.
- Границы явно отделяют включённое изменение от связанных работ вне объёма. Не расширяй объём из похожей задачи.
- Отдельные критерии приёмки нужны, когда добавляют условия проверки, сочетание требований или пример границы. Проверяемые функциональные требования не переписывай вторым списком.
- Размер описания соразмерен неопределённости и риску. Необязательные разделы удаляй; один факт держи в одном месте.
