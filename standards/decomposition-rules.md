# Правила декомпозиции

Подзадача выделяется по самостоятельному результату, ответственности или существенной зависимости. Не создавай отдельные задачи «прочитать», «подумать», «написать код» без самостоятельного проверяемого результата. Простое изменение может потребовать одну подзадачу разработки, с проверкой внутри её объёма.

Перед предложением работ сопоставь требования с существующими подзадачами по результату и границам, а не только по названию. Для каждой работы выбери действие: `reuse` — использовать существующую, `update` — предложить изменение существующей, `create` — новая. Не удаляй и не закрывай лишние задачи без отдельного поручения; обозначь проблему в отчёте.

Используй нужные категории из справочника скилла декомпозиции. Дизайн нужен при требуемом проектировании взаимодействия; аналитика — для конкретного нерешённого вопроса или контракта; отдельное тестирование — при самостоятельном результате проверки. Наличие категории в каталоге не является основанием создать задачу.

Составь покрытие: `требование → существующая/предложенная работа → способ проверки`. Для требования без новой работы укажи причину: например, оно покрыто существующей задачей или подтверждённой функцией. Не прячь пробел за формулировкой «учесть все требования».

Зависимости описывай по результату: что должно быть получено до начала конкретной работы. Отличай блокер от порядка, удобного для исполнения. Если анализ или дизайн меняет будущий объём разработки, пометь разработку как предварительную и укажи условие уточнения. Цикл зависимостей нужно разрешить, а не объявить готовностью.

Метаданные типов берутся из целевого проекта или трекера. Если они неизвестны, подготовь категории и содержание без точных типов и ID, перечисли препятствия для записи. Обнаруженный дефект оформляй как `subbug` только при доказанном расхождении ожидаемого и фактического поведения; недостаток требований — аналитический вопрос.
